# AGENTS.md – ASUS DialPad Driver

## Workflow / architecture

- **Name:** the project is shown as **Turnpad**; the technical name is `asus-turnpad`. All identifiers live in `config/identity.py` (Python) and `install_paths.sh` (shell); `tests/test_identity.py` keeps them and their JS/JSON/.desktop twins in sync. "DialPad" in docs names the ASUS hardware feature.
- **Modes** (names used in the UI and docs): **DialPad mode** (ASUS laptop with the printed DialPad: layouts, calibration, hidraw/I2C light), **Touchpad mode** (any other touchpad: config `emulation`, `dial_gesture.emulated_dial`), **Mouse-only mode** (no touchpad, a mouse: config `mouse`, `mouse_dial.py`, `MouseSource` in `listen_input_sources`), **SpaceMouse mode** (a 3Dconnexion SpaceMouse through spacenavd: config `spacemouse`, `spacemouse_dial.py`, `spacenav_client.py`, `SpaceMouseSource`). In code and config the first is the default, the second is "emulation", the third "mouse mode", the fourth "spacemouse mode".
- **Supported desktops:** GNOME (Shell extension) and the Wayland compositors with layer-shell: KDE Plasma 6, Hyprland, sway, niri, COSMIC (layer-shell dial `overlay/layer_shell.py`; sway tested in CI, KWin by hand with a GPU render node, the others untested). X11 sessions keep the legacy PySide window `dialpad_ui.py`. Other desktops start with an issue (`.github/ISSUE_TEMPLATE/desktop-support.yml`); do not add one unasked.
- **Before the rename** the project was installed as `asus-dialpad-driver` (`/usr/share/asus-dialpad-driver`, `~/.config/asus-dialpad`, D-Bus `io.github.asuslinuxdrivers.DialPad`, extension `dialpad@asus-linux-drivers`, services `asus_dialpad_driver@$USER`). `install_migrate.sh` moves settings and removes those leftovers on every install and uninstall.
- **Agent skills** (`.claude/skills/`, checked by `tests/test_skills.py`): `app-plugin` (add-ons and bridges for applications; `scaffold_bridge.py NAME --title --desktop-id [--link-app] --wire` writes a bridge on `integrations/bridge_base.py` and registers it in every list), `app-pack` (packs in `config/presets.py`; `pack_report.py` prints one as tables), `turnpad-checks` (`checks.py [--baseline]` picks the checks for the changed files; `--baseline` runs the suite on the base in a worktree to tell regressions from a container's missing GTK/gjs/libevdev), `ship-files` (where a new file, service or library must be listed), `driver-edit` (CRLF, threads, contracts of `dialpad.py`). Keep a skill in step when its facts change.
- **Root:** Single-repo, single-app. No monorepo, no build steps; unit tests in `tests/`.
- **CI:** `.github/workflows/tests.yml` on GitHub Actions (every push and pull request) runs in an `archlinux:latest` container (Ubuntu's GTK/Libadwaita are too old): unit tests including the headless-mutter layout test, syntax checks, and `update_previews.py --check --only overlay`; job `arch-package` runs `packaging/arch/test-package.sh` (builds the Arch package from the commit, installs, checks files and imports, removes); jobs `deb-package` (ubuntu:latest, ubuntu:24.04, debian:trixie) and `rpm-package` (fedora:latest) do the same for `packaging/deb` and `packaging/rpm`; job `install` runs `tests/install_in_container.sh` (fedora:latest, ubuntu:latest, ubuntu:24.04; a GNOME and a sway install); job `layer-shell-dial` runs `tests/layer_shell_in_container.sh` on headless sway at scale 1 and 2 (artifact `layer-shell-dial`). Settings pictures are only rendered and attached to the run (artifact `rendered-pictures`): they show the apps installed on the desktop that renders them (Krita, Firefox, darktable icons), so they are updated locally.
- **Entrypoints:**
  - `dialpad.py` – main driver daemon, ~3000 lines, monolithic. Runs as the user service `asus-turnpad.service` with the system `/usr/bin/python3`.
  - `dialpad_ui.py` – legacy PySide6 overlay for X11 sessions, separate `asus-turnpad-ui.service` (template `asus-turnpad-ui.x11.service` only). On GNOME replaced by `gnome/extension/`, on other Wayland desktops by `overlay/layer_shell.py`.
  - `install.sh` – bash installer for every distribution (unattended; `--interactive` asks), sources sub-scripts from repo root. Refuses to run while the Arch package is installed. Installs distribution packages only (`install_packages.sh`: groups per package manager, optional ones one by one); no venv, no pip, no compiler or `-dev` headers (`tests/test_install.py` maps every imported library and GI namespace to its package).
  - `packaging/` – distribution packages: `arch/PKGBUILD` (`asus-turnpad-git`, builds the latest GitHub commit; deps from the Arch repos, no venv), static user units `asus-turnpad.service` (layout `auto`) and `asus-turnpad-overlay.service` (layer-shell dial), udev rules (uaccess + groups), modules-load, sysusers, and `asus-turnpad-setup` (per-user: groups, enable the driver service, then the extension on GNOME or the dial's service on other Wayland sessions when `Gtk4LayerShell` imports; runs under `set -u`, so `${XDG_CURRENT_DESKTOP:-}`; refuses while an `install.sh` install exists). `gtk4-layer-shell` is optional: PKGBUILD optdepends, deb/rpm Recommends. `arch/build.sh` runs `makepkg -si` in `~/.cache/asus-turnpad/makepkg` (makepkg rewrites `pkgver` in the PKGBUILD it uses, which would dirty the clone); `arch/test-package.sh` tests it in a clean container. `install-files.sh <root> [--no-bytecode]` is the one file list of all packages (PKGBUILD, `deb/debian/rules`, `rpm/asus-turnpad.spec` call it; every root `*.py` but `dialpad_ui.py`, explicit extension files). `deb/` (debhelper, `dh_python3` compiles at installation, the user unit is not enabled globally) and `rpm/` (spec, `%py_byte_compile`) each have `build.sh` (`git archive` of HEAD, a commit or `--worktree` into a temp dir; version `0.r<commits>.<hash>`; output in `~/.cache/asus-turnpad/{deb,rpm}`) and `test-package.sh` (apt/dnf install without recommends, files, `check-imports.py`, `asus-turnpad-setup` as a user, remove). Their dependency lists match `install.sh`; Fedora also needs `gobject-introspection` (cairo typelib). `tests/install_in_container.sh` runs `install.sh` + `uninstall.sh` in Fedora/Ubuntu containers (CI job `install`); `INSTALL_IN_CONTAINER=1` (install_common.sh) skips the touchpad check, modprobe and starting services. The settings app needs Libadwaita 1.5 and GTK 4.14 (Ubuntu 24.04, Debian 13); newer widgets get a fallback (`_page_sidebar()` for `Adw.ViewSwitcherSidebar`, `_button_row()` for `Adw.ButtonRow`), and `install.sh` warns below 1.5. Users read `INSTALL.md`.
- **Install target:** `install.sh` → `/opt/asus-turnpad/`, owned by root, system Python (`PYTHON` in `install_paths.sh`) (FHS layout in `install_paths.sh`); Arch package → `/usr/share/asus-turnpad` (`identity.PACKAGE_DIR`), system Python. Code must not assume either path (it finds files next to itself). User data: `~/.config/asus-turnpad/` (`config.json`, `skins/`, driver state `dialpad_dev`). Source and installed versions can diverge; diff before debugging.
- **Fork additions:**
  - `layout_detect.py` – layout for this laptop from `laptop_touchpad_dialpad_layouts.csv` (product name, then touchpad vendor/product id; fallback `proartp16`). `dialpad.py auto` uses it; `install_layout_auto_suggestion.sh` runs it as a script. Nix packaging was removed (stale, old names).
  - `dialpad_dbus.py` – session D-Bus service (`io.github.sinu0.AsusTurnpad.Driver`), signal `OverlayState(bsasasidsbbb)`.
  - `dial_gesture.py` – pure gesture maths (angle, slices, `RotationTracker`), no hardware imports; unit tested.
  - **Security:** services keep `NoNewPrivileges=yes` (dial commands must never reach root, the user may have passwordless sudo); the driver needs no privileges (I2C via group, hidraw via uaccess). `config.schema.shell_commands()` lists commands of imported profiles and the app asks before importing them. Skins must stay data only.
  - `launch.py` – runs Command/Shell steps: in their own `systemd-run --user --scope` (they survive driver restarts), waiting at most 2 s so a program with a window never blocks the action thread. Functions with no turning actions are launchers: `select_multifunction_segment()` runs their tap action straight from the menu (library category "Launch").
  - `backlight.py` – DialPad light brightness: `commands_for_level()` (0 = light off while the dial works, 1–8 = values `0x41`–`0x48` after `0x01`) and `KeyboardBacklight` (UPower `KbdBacklight` on the system bus, keyboard off = light off; change signals arrive in the D-Bus service's GLib loop). Config section `backlight` (`follow_keyboard`, `level`); the driver applies it through `apply_backlight()` on the action thread, never on the touch thread.
  - `tests/` – `unittest` suite for gesture maths, legacy adapter and D-Bus overlay state.
  - `config/` – JSON config model, macro runtime, legacy adapter, migration from old `dialpad_dev` INI + `layouts/*.py`.
  - `config/presets.py` – ASUS Dial-style function library (categories in `LIBRARY_CATEGORIES`, ready groups in "Groups": Apps, Clipboard, Media controls, System, Navigation, Documents) and pre-programmed app packs. Every `AppPack` has a basic variant (`factory`, ≤ 6 functions, no groups) and an advanced one (`advanced`, ≤ 8 sectors with groups by the stages of the work, `advanced_look` = the profile's dial look, e.g. the menu at the top for timeline editors); `profile_for_app(name, app_id, advanced)`, `profile_for_pack(pack, advanced)`, `variant_summary()`; the settings app asks which (`_choose_pack_variant()`). Function looks `CANVAS` (pill), `VIEW` (fade) and `TIMELINE` (top, fade) keep the dial off the work. Shortcuts are the applications' defaults, checked against their sources (comment per pack); keys go to the window under the pointer. `tests/test_presets.py` checks sizes, unique titles, evdev key names, valid looks, round trips and which pack matches which desktop ID. `suggested_color()` colours functions without one. Packs also carry SpaceMouse buttons (`AppPack.spacemouse` / `spacemouse_advanced`, built fresh by `spacemouse_buttons(advanced)`, applied into `Profile.spacemouse_buttons` by `_pack_profile()`): the five function keys short (12–16) and long (17–21) as press actions only (a long press may be `key_hold`, e.g. Blender pie menus), Fit and the view keys where the application has shortcuts, `none` where it reads the 3D mouse itself (Blender: view keys, Fit, Roll, Esc/Alt/Shift/Ctrl, +/−), a `label` ≤ 20 characters per bound entry for the device screen; Menu (0) and the motion keys stay with the global map. FreeCAD's own 3Dconnexion button map is empty until loaded in its Customize dialog, so its view keys press its view shortcuts (1–6, 0, V, F). Key sequences ("V, F") are one keystroke step per press. Packs: GIMP, Krita, Inkscape, darktable, Blender, FreeCAD, SolidCraft (category "3D"; SolidCraft's steps are `app` steps with its own keys as fallback, see the SolidCraft bridge below), KiCad ("Electronics", app id `org.kicad.pcbnew.desktop`, no view keys), Kdenlive, DaVinci Resolve (shortcuts from third-party sources only); `tests/test_presets.py` checks labels, indexes, evdev names and round trips.
  - `config/profile_share.py` – profiles as text: `PROFILE_FORMAT` + `ai_prompt()` for assistants, `profiles_from_text()` reads an answer, a profile or an export file (normalises key names via `labels.parse_keys`, raises `ProfileTextError` with a readable reason); used by Dial Controls › Build with AI and by file import. Keep `PROFILE_FORMAT` in sync with the schema.
  - `config/labels.py` – key/macro labels shared by the GUI and the overlay hints (includes the evdev code table for old numeric keys); `parse_keys()`/`keys_to_text()` read and write typed shortcuts ("Ctrl+F12"); `ICON_RULES` must match `dial.js` (`tests/test_labels.py`), `ICON_CHOICES` feeds the icon picker.
  - `config_app/` – GTK4/Libadwaita settings GUI (`io.github.sinu0.AsusTurnpad`).
  - **Screen page** (settings app, `config_app/main.py` section "Screen" + `config_app/screen_page.py`, GTK-free helpers tested by `tests/test_screen_page.py`): status (device, `systemctl --user is-active` of `SCREEN_SERVICE` off the main thread, pyusb hint, the switch for `screen.enabled` starts/stops the unit after saving), a preview (`screen.preview.render()`, imported lazily; `_ScreenPicture` gives the 4:3 picture its height from its width, a scrolled page gives widgets only their minimum height), Look, Power, Pages (order, shown, start page, follow dial), Per application (profile overrides `Profile.screen`, accent, labels of the function keys), help for the screen keys. The page (`_screen_page`, an `Adw.ViewStackPage`; the sidebar fallback follows `visible`) shows while `screens_present()` finds a screen or any `screen` setting differs from the defaults (`settings_customised()`); `_refresh_screen_presence()` runs at start and from every Driver page refresh. A function key's label is `SpaceMouseButton.label` of the effective binding: for a scope without an own entry `set_label()` stores a label-only entry (`SpaceMouseButton(label=…)`), which keeps the actions below it (`merge_spacemouse_buttons()`, `sm.binding()`). Settings apply through the normal save path; a file monitor on `config.json` takes an externally saved `screen` section (the screen service saves quick settings) unless the window has unsaved changes. `tests/layout_probe.py` forces the page with a fake `screens_present`.

A group's list is a separate actor (child of the dial) painted by `paintSubmenu()`, placed by `submenuPlacement()` beside the dial on the dial's monitor (side of the group's sector, smaller rather than over the dial on a small screen, also next to a dial at position `pointer`; `tests/test_overlay_placement.py`) and slid in with an ease. Shape paths exist twice: `shapePath`/`tilePath` in `dial.js` and `shape_path`/`_tile_path` in `overlay/painter.py`; `tests/test_skins.py` checks the shared lists and limits.

Stops after 10 s without a key; Append/Replace when the macro has steps. Without a readable keyboard (no `input` group) the dialog says so and records the GTK key events of its own window (`gtk_event()`); the dialog swallows keys while counting and recording so Tab/Enter/Esc do nothing in it.

Keep geometry in sync with `dial.js` (also `paint_submenu()` with `paintSubmenu()` and the `LIST_*` constants).

GTK 4 + `Gtk4LayerShell`: overlay layer, no keyboard, empty input region, the compositor picks the output (`--output NAME` pins it). Run with the system `python3`; it restarts itself once with gtk4-layer-shell in `LD_PRELOAD`.   - **SpaceMouse cap motion per application**: `SpaceMouseConfig.motion` and `Profile.spacemouse_motion` (`_meta.spacemouse_motion`) are override dicts normalised by `motion_rule()`: `sensitivity` 0.1–4, `axis_sensitivity` [X Y Z RX RY RZ] 0–4 (0 locks an axis), `invert` [6], `rotation`, `translation`; `effective_motion(global, profile)` gives all five. They are factors on spacenavd's own configuration, not absolute values: sensitivity and axis sensitivities multiply the daemon's, invert flips its flag, a disabled group is 0, so the default motion changes nothing and sends nothing. `SpaceMouseSource.sync_motion()` (every pass, after the mute decision) compares the target (`motion_target()` = effective motion with the focused app id's `MotionSession` on top) with the last applied one and, when it differs, reads the daemon's values once (`GCFG_SENS`, `GCFG_SENS_AXIS`, `GCFG_INVERT`; while muted the saved sensitivity), puts them into the restore file under `motion` (`sens`, `axis`, `invert`) before the first change, and sets `motion_values(original, target)`; a neutral target sets the originals back and clears the entry. The restore file is also processed by `restore_spacenav_leftovers()` (next connection, driver start); exit (`close()`) gives the originals back after the unmute, and a lost connection forgets the in-memory state but leaves the file. Mute interplay: while muted (dial on or a Control `mute:MS` lease) a motion change updates `saved_sensitivity` (and the restore file) instead of sending the sensitivity, so unmuting restores the profile's value, never the original. Session toggles (`SpaceMouseAction("motion", motion=rotation|translation|faster|slower|reset)`) live in `MotionSession` per app id (`app_name`) for the driver run, are not saved, and `faster`/`slower` step through `SPEED_STEPS` (0.1 … 4). `DriverState.motion` = `{sensitivity, rotation, translation}` of the focused application (`SpaceMouseSource.motion_shown`).
  - **SpaceMouse page: layers, motion, app commands, Blender add-on** (settings app; GTK-free logic in `config_app/spacemouse_extra.py`, widgets in the mixin `SpaceMouseExtras` of `config_app/spacemouse_ui.py` that `Application` inherits, `tests/test_spacemouse_extra.py`; every module is listed in `install.sh`). Layer selector under *Applies to*: Base + the scope's layers (a profile also sees the global ones, marked "from All applications", and edits its own map of that name; renaming a global layer renames the profiles' maps and every `layer` action, removing asks and turns the actions that switched to it into `none`); with a layer selected the key list shows `current_binding()` (the layer's own entry, else the global layer's, else the base binding, "from base", dimmed) and the button dialog has an "Own binding in the layer" switch (`store_binding()`/`drop_binding()`; an explicit `none` press passes through in the layer). Action editor types *Switch layer* (layer combo + "New layer…", mode Hold/Once/Toggle = `hold`/`latch`/`toggle`), *Cap motion* (`rotation`, `translation`, `faster`, `slower`, `reset`) and *App command* (`ActionExtras`: `GetAppCommands(<profile app_id>)` → searchable picker grouped by category with the default keys; without a catalog, or for All applications, a free command id; the fallback keys entry is always there and is filled from the command's default keys when empty); `is_valid()` drops a layer without a name and an app command without an id, as the schema does. *Cap motion* group: global (`SpaceMouseConfig.motion` keeps only values that differ from `MOTION_DEFAULTS`, `{}` = leave spacenavd alone) or a profile's override with "Use the global settings" (an override is a full snapshot); sensitivity slider (log scale, 1 in the middle), rotation/pan switches, an *Axes* expander (six sensitivities, six invert switches); a status line from `GetDriverState` (`motion`), polled every 2 s while the page is visible. *Blender* group (shown with a Blender profile or `blender` on the PATH): status from `GetAppCommands("blender")`; *Install the Blender add-on* (`config_app/blender_addon.py`, in a thread) runs `blender --command extension build --source-dir <program dir>/integrations/blender/turnpad --output-dir ~/.cache/asus-turnpad/blender`, then `blender --command extension install-file -r user_default -e <zip>` (verified with Blender 5.2.2 and `BLENDER_USER_RESOURCES`); without Blender or when a command fails it builds the zip with `zipfile` (files at the zip root, no caches) and shows the manual steps (Edit › Preferences › Get Extensions › Install from Disk); a result dialog shows the log. Both `shell_commands()` callers in `main.py` get the global layers (tested). `tests/layout_probe.py` `spacemouse_extra_dialogs()` covers the new pages and dialogs.
  - **Touchpad mode** ("DialPad emulation"; config section `emulation`: `enabled`, `corner`, `center_size`; settings app *Driver* page) for touchpads without a DialPad: read once at driver start (the app runs `systemctl --user reset-failed` + `restart`), any touchpad (`layout_detect.is_touchpad()`), no hidraw/I2C and `send_value_to_touchpad()` sends nothing. Geometry from `dial_gesture.emulated_dial()` (ring = whole touchpad, centre = `center_size` % of the shorter side, 15 mm corner, `x_scale` for unequal axis resolutions). While on, `set_emulated_dial_owns_touchpad()` grabs the evdev device and disables send-events (on the action thread), so libinput resyncs when it gets it back; every touch is the dial except one that starts on the corner. The driver starts with it off, re-enables send-events at start and on SIGTERM (emulation only), refuses calibration. Tests: `tests/test_emulation.py`.

Grammar: `toggle`, `dial-on`, `dial-off`, `rotate:N` (N -10..10 except 0, clockwise when positive, only with the dial on), `select`, `back`, `function:N` (menu slot from 0, switches the dial on), `function=TITLE`, `group` (first group), `group=TITLE`, `button:INDEX` (press action of the effective SpaceMouse button INDEX; `false` for `modifier`, `key_hold`, `none` and unbound buttons), `mute:MS` (MS 0..5000: silence the other spacenavd clients for MS milliseconds, 0 ends it; a lease, not a queued command — `on_dbus_control()` grants it at once on `spacemouse_mute`, a `MuteLease` of `spacemouse_dial.py`; `SpaceMouseSource.sync()` mutes while `spacemouse_mute.wanted(dial, mute_others, now)` = the dial is on with `mute_others`, or a lease runs, through the same sensitivity-0 + restore-file machinery, so it works with `mute_others` off too; only in SpaceMouse mode with spacenavd v1 connected, else accepted and ignored; the lease is never longer than 5 s, so a program that crashed lets go by itself). ## Config migration behavior

- First launch of the Turnpad app migrates old `dialpad_dev` INI + `layouts/proartp16.py` into `~/.config/asus-turnpad/config.json`.
- If JSON exists, migration is skipped. To re-migrate: delete the JSON file first.
- The driver loads JSON config at startup if it exists; otherwise falls back to legacy layout Python.
- Macros (`MacroStep` list) appear as `{"macro": [...]}` inside legacy `app_shortcuts` dict entries. `emulate_shortcuts()` handles them before legacy key/command logic.

## Profiles and dial behaviour (ASUS Dial parity)

- **App link** (`app_link.py`, started by `start_app_link()` in `dialpad.py` after `init_dbus()`): the driver is the server of the Unix socket `$XDG_RUNTIME_DIR/asus-turnpad-apps.sock` (`config.identity.app_link_socket_path()`, twin `SOCKET_NAME` in `integrations/blender/turnpad/protocol.py`), in a thread of its own, mode 0600 in a runtime directory that must be the user's alone (checked: not a symlink, uid, no group/other bits; no runtime dir = no link, never `/tmp`), peers checked with SO_PEERCRED, a stale socket removed and a live one (another driver) left alone. Newline-delimited JSON, lines of at most 64 KiB (longer drops the client); client → driver `hello` (`app`, `name`, `version`, `pid`, `protocol` 1; nothing counts before it, answered with `{"hello": {"protocol": 1}}`), `commands` (the catalog, at most 500 entries, entries cleaned: id `[A-Za-z0-9_.:-]{1,128}`, title, category, icon, keys, modes; a longer catalog is ignored and the old one stays), `context` (`mode`, `label`, `detail`, on every change), `result` (`seq`, `ok`, `error`); driver → client only `run` (`id`, `seq`). **Nothing received is ever executed by the driver**: `AppLink.run(window_id, id)` sends a `run` only when the id is in the catalog of the same client (the most recently active client whose `app` matches the focused window, `app_matches()`: `blender` is `org.blender.Blender.desktop`, `/usr/bin/blender`, `Blender`), else it answers `unknown-command`/`no-client`/`busy`. `run_app_command()` (action thread) falls back to the step's keys when the outcome is not `sent`, without keys it logs and sets DriverState `notice`; a failed `result` also sets a notice. A link change (hello, context, gone) sets `pending_context_refresh`, so the input loop looks at the profile contexts again. Macro step `app` (`StepType.APP`: `command`, optional fallback `keys`; `MacroExecutor(run_app=...)`) and SpaceMouse action `app` (`command`, `keys`; `SpaceMouseAction.steps()` makes the step) use it; `keys` of app steps are enabled on the virtual keyboard. The Blender add-on is `integrations/blender/turnpad/` (shipped by `install.sh` and `packaging/install-files.sh`; `tests/test_app_link.py` speaks the wire format with a fake client).
- **Bridges** (`integrations/bridges.py`, started by `start_bridges()` from `start_app_link()`, stopped in `stop_app_link()`): for applications that have a control channel but no add-ons. `BridgeHost` runs every module of `BRIDGES` on one thread `asus-turnpad-bridges`; `integrations/bridge_base.py` `LinkedBridge` is the shared life of a bridge (subclass: `candidates()` → `[(key, candidate)]`, `connect(candidate)` → a session with `version`, `entries`, `detail`, `alive`, `run(id)` → (ok, error), `poll()` → context, `close()`; errors `BridgeError`/`BridgeGone`; a candidate that fails rests `REFUSE_S`). New bridges: `.claude/skills/app-plugin` (`scaffold_bridge.py`) (a module has `NAME` and `create(socket_path)` → object with `tick()` → seconds to the next pass, never blocking long, `stop()`, `status()` → JSON-able dict; one that raises is logged and rests `FAILURE_REST_S`). A bridge joins the app link like an add-on through `integrations/applink/` (`protocol.py`, `client.py`: twins of the Blender add-on's, which is zipped on its own; `tests/test_bridges.py` compares their code without the docstring), so the driver's rules hold: it sends `run` only for ids of the bridge's own catalog. `GetStatus` carries `bridges` (JSON text of `{name: status}`). Packaging: `integrations/*.py`, `integrations/applink/*.py` and each bridge's `*.py` in `install.sh` and in the `for dir in` list of `packaging/install-files.sh` (`tests/test_install.py` `BRIDGE_PACKAGES`); `packaging/check-imports.py` imports them.
- **SolidCraft bridge** (`integrations/solidcraft/`, user guide `SOLIDCRAFT.md`): SolidCraft (Rust CAD, desktop id `ai.storyteller.solidcraft`) answers JSON lines on `127.0.0.1:PORT` when started with `SOLIDCRAFT_CONTROL_PORT`/`--control`; the first request carries the per-launch token from `<data>/solidcraft/control/PORT.token` (`control.token_dirs()`: `SOLIDCRAFT_CONTROL_DIR`, XDG data, Flatpak, Snap; only regular 0600 files of this user, read with `O_NOFOLLOW`; a port another uid listens on is refused via `/proc/net/tcp`, `port_owner()`). `ControlClient.call()` times out after 3 s and then closes (a late reply would be another request's). On link: `ui.help` (version), `engine.commands` → `catalog.wire_catalog()` = the bridge's `VIEW_COMMANDS` (`turnpad.*`: orbit/roll 5° via `ui.camera`, 90° rolls and pan via `engine.execute view.navigate`, views via `ui.view` animated, `ui.palette`) then toolbar commands + `EXTRA_COMMANDS`, ≤ 500; hello app `solidcraft`, pid 0. `runner.Runner` sends SolidCraft commands as `ui.start` (the toolbar's path), but a SKETCH-tab tool with a one-key shortcut outside a sketch as `ui.key` (only the key opens Create Sketch and starts the tool). Context every 0.5 s from `ui.inspect`: mode = ribbon tab (`catalog.mode_of_tab`: `model`, `sheet_metal`), detail = tool label or dialog kind; catalog modes and categories use the ribbon too (`catalog.PLACEMENTS`, twin of `PLACEMENTS` in SolidCraft's `crates/ui-egui/src/workspace.rs`: a command's `SOLID` tab shows as `MODEL`). Run against a live SolidCraft 0.18.1 (headless: `xvfb-run solidcraft --control PORT` with Mesa's lavapipe Vulkan; orbit, tilt, zoom, pan, 90° roll, views, Create Sketch for a sketch key, Extrude dialog all worked). Token files that lead nowhere rest `REFUSE_S`. Facts were read from SolidCraft's source at 41a62d2 (`docs/control-protocol.md`, `crates/ui-egui/src/control.rs`, `keymap.rs`, `toolbar.rs`, `navigation.rs`); re-check them when SolidCraft changes. `tests/fake_solidcraft.py` is a fake control channel; `tests/test_bridges.py` runs driver → bridge → fake end to end. The *SolidCraft* pack (`config/presets.py`, category 3D) uses `app_step()` / `_app_press()` with SolidCraft's default keys as fallback (`tests/test_presets.py` `SOLIDCRAFT_COMMANDS` checks ids and keys); SolidCraft ignores 3D-mouse buttons, so the pack binds all view keys.
- **Contexts** (`Profile.contexts: list[ProfileContext]`, `config/schema.py`): `name`, `title` (plain text, no regular expression because `re` holds the GIL and a pattern like `(a|a)*b` would freeze the driver: the first 500 characters of the window title, case-folded, contain any of the `|`-separated alternatives, each stripped, empty ones ignored; at most 200 characters and one non-empty alternative, checked by `context_title_error()`; matching is `context_title_matches()`, the settings app uses the same function), `app_modes` (modes the app link reports), `segments` (own dial menu, `None` = the profile's), `spacemouse_buttons`/`spacemouse_layers` (laid over the profile's), `screen` (over the profile's). A context matches when every given condition does (it needs at least one); the first match wins, none = the plain profile. The legacy adapter derives one complete shortcut set per context under the profile's reserved `_contexts` key (`[{"context": ProfileContext, "shortcuts": {...}}]`, `shortcuts_for_context()` picks); its `_meta` is a dict of its own (`context` = name, merged buttons/layers/screen, the profile's motion), so `profile_meta()` changes with the context (D2's layer/hidden-button logic watches `id()`). `select_profile_context()` runs in `window_was_changed()` with the title (`pushed_window_title` from `SetActiveWindow`, else the polled `window_title`) and the mode from the link; the dial restarts only when the menu titles differ, `last_function_by_app` is keyed `(app, context)` when a context is in force, DriverState has `context`. `profile_share` validates contexts (and `app` steps/actions); `PROFILE_FORMAT` documents them.
- **Profile offers** (`app_suggest.py`, `desktop/notifications.py`): on a real focus change to an application without a profile (`app_name == "none"`) whose id matches a pack (`presets.pack_for_app`), `suggest_profile()` offers the ready profile once per application id (remembered in `~/.config/asus-turnpad/suggested.json`, written before the offer): DriverState `suggest` for ~20 s and a notification (`org.freedesktop.Notifications` through the driver's own session connection) with the button "Create profile", which runs `<python> <program dir>/config_app/main.py --add-profile <app id>` through `launch.run` in a thread. Not for configuration reloads.

- Profile fields: `mode` (`multi` radial menu / `single` bound function + `single_function`), `sensitivity` (divides rotation thresholds), `scroll_speed` (multiplies scroll units), `remember_last`.
- Segment fields: `enabled`, `color`, `with_modifier` (`{"Ctrl"|"Shift"|"Alt": ModifierActions}`, own `macro_cw/ccw/center` while that key is held; `MODIFIER_KEYS` in `config/schema.py`), `items` (a list makes the segment a group; `None` = a function). Groups go one level deep (the decoder drops `items` of items), have no actions of their own, and a group without enabled items is left off the dial; `single_segment()` never binds a group. The legacy adapter writes a group as `{"items": {title: legacy segment}, "icon": GROUP_ICON, …}`; `config.schema.all_functions()` walks functions inside groups too (`shell_commands()` names them `Group › Function`). The adapter adds them as entries with `"modifier": [left, right key names]` after the plain entry; `shortcuts_for_modifiers()` in the driver runs the entries of a held key, otherwise the plain ones (a function without a variant keeps working while a key is held). The keyboard listener only follows keys in `modifiers`, which `enable_config_macro_capabilities()` fills from these entries. Use `Segment.macro_lists()` for anything that must see every step (`shell_commands()`, import checks). MacroStep scroll fields: `axis` (`horizontal`), `modifiers` (keys held while scrolling, e.g. Ctrl = zoom). Never reuse a scroll step's legacy `keys` (old configs contain junk like `["8","11"]`).
- The legacy adapter puts profile settings under the reserved `_meta` key; `is_multifunction()` skips keys starting with `_`. Single mode uses the flat `clockwise/counterclockwise/center` layout with `_meta.single` holding title/treshold/value/unit/color/hints.
- In a selected function: tap centre = the function's `macro_center` if any, otherwise back to menu; holding the centre for `gesture.center_hold_time` returns to the menu (fires while still touching).
- Groups: choosing a group's sector opens its list (`open_submenu()`; driver globals `submenu` = group title, `submenu_index`); turning moves the highlight one item per `SUBMENU_STEP_DEGREES / sensitivity` and stops at the ends, lifting the finger keeps the list, a centre tap runs `select_multifunction_segment()` on the highlighted item (a launcher runs and the list stays), holding the centre runs `leave_function()`: one level back, from a function of the group to its list, from the list to the menu. `function_entry()` looks a title up in the open group's items, else in the menu; use it instead of `app_specific_shortcuts[title]`.
- Dial look per level: `overlay` defaults (`position` incl. `custom` + `custom_x`/`custom_y` = dial centre as screen fractions and `pointer` + `pointer_side` (`POINTER_SIDES`, default `below-right`) / `pointer_gap` (logical px 0–400, default 24, not multiplied by `scale`), `visibility` `full`/`fade`/`pill`, `fade_opacity` %) ← `Profile.overlay` ← `Segment.overlay` (dicts of overrides, validated by `overlay_rule()`). The driver merges profile + function (`overlay_look()`, also in single mode via `_meta.single.overlay`) into `details.look`; the menu uses the profile's. The extension resolves the rest with `effectiveLook()` in `dial.js`; `fade` = full on touch, fades after `FADE_AFTER_MS`; `pill` = a small St label (`pillContent()`/`pillPlacement()`) instead of the dial. Settings app: `_dial_look_rows()` (plain on the Skins page, folded "On-screen dial" row in profile and function editors, screen picker for custom, side and distance rows for "Near the pointer").
- Position `pointer`: `besidePointer()` in `dial.js` (twin `beside_pointer()` in `overlay/look.py`) puts the dial's box (dial + hints; the pill likewise) on the chosen side of the pointer, `pointer_gap` away, straight sides centred on it. A side without room flips to the opposite one, a straight side then tries the two across it; the box is then clamped on screen and covers the pointer only when no side leaves room. The pointer is read only when a fully hidden dial shows (`_followPointer()`; fading counts as shown), so the dial never moves while visible, also not on a look change; without a known pointer it is `lower`.
- `last_function_by_app` holds `(group, function)` (group `None` in the menu) and restores the last function on activation and focus change; returning to the menu or to a group's list forgets it. A focus change to another app never keeps the previous app's function.
- `overlay` section of config.json (scale, position, hide_delay_ms, show_hints, show_pointer, accent, skin, skin_light, follow_system_style) is read directly by the Shell extension through a directory monitor (also on the skins directory); the driver does not use it except `show_pointer`. With `follow_system_style` the extension uses `skin_light` unless `org.gnome.desktop.interface color-scheme` is `prefer-dark`.
- `tests/test_driver_state.py` extracts the state functions from `dialpad.py` via AST; keep their names in `STATE_FUNCTIONS` in sync when renaming.

## Guided calibration and other models

- `dial_gesture.CalibrationSession` (pure, tested) fits the outer ring and the centre button from finger traces (`fit_circle`, `angular_coverage`). The driver routes whole touch frames to it while `calibration` is set and skips activation and dial actions; send-events are disabled meanwhile.
- The settings app applies the result live and asks *Keep* / *Revert* (`_calibration_backup` holds the geometry before; closing the app without choosing reverts in `do_shutdown`). It stores `device_name` = layout; `apply_gui_settings()` ignores JSON geometry whose `device_name` differs from the running layout.
- *Reset geometry* restores the running layout's values via `config.migrate.layout_geometry()`, which parses the layout file with `ast` (layouts import `libevdev`); the toast offers Undo.
- First-run migration detects the layout via `GetStatus()` or the `dialpad.py` process arguments — never hard-code `proartp16`.
- `details` payloads never go to the Unix socket (the PySide overlay `dialpad_ui.py` reads newline-delimited JSON and applies only the keys present).
- See `PORTING.md` for the user-facing steps.

## Touch input pipeline

- Frame-based processing in `listen_touchpad_events()`: events buffered per slot, gesture logic runs once per `SYN_REPORT`.
- Global state mutation is serialised through `driver_state_lock` and `process_pending_driver_updates()` called at start of each frame.
- Per-frame recalculations of `circle_radius` and bounds allow live calibration changes.
- Constants: `DEBOUNCE_MS=30`, `SETTLE_FRAMES=3`; hysteresis comes from `gesture.hysteresis` in JSON (default 3 without JSON).
- `RotationTracker.reset()` must run on touch down, lift, centre and leaving the ring, or the next touch jumps.
- `finger_down` follows the one finger the dial tracks (`dial_touch_id`, chosen by `dial_gesture.select_dial_touch`): the touch already followed, else the newest touch inside the ring or on the corner icon. Other fingers, a resting palm and touches reported as `MT_TOOL_PALM` are ignored, and lifting the tracked finger counts as release even while others stay down. Never clear `slots` on release; `update_touch_slots()` keeps them in sync (also from `d_t.sync()` after `SYN_DROPPED`).
- Actions, shell macros and value queries run on the `dialpad-actions` worker thread via `enqueue_action()`; never call subprocesses from the touch loop.
- Configuration reloads and application changes wait while the dial tracks a finger (applied at the end of the lift frame); calibration requests do not.
- Every send to the virtual device holds `uinput_lock`; `reset_udev_device()` (on the action thread after a reload, on the keymap threads otherwise) swaps the device under it, releases held scroll modifiers on the old device and destroys it with `close_virtual_device()` (python-libevdev's reference cycles would keep it alive).
- The GNOME overlay shows while `touching`, and fades out 1.5 s after release. It appears on the monitor with the pointer (`_followPointer()` in `extension.js`) and stays there while visible, even if the pointer moves to another monitor; only a fully hidden dial follows the pointer again. The layer-shell dial gets the same effect from the compositor: its window is unmapped only when fully hidden, so the compositor picks the output again on the next show. With position `pointer` it asks `desktop/pointer.py` at that moment (Hyprland only, a local socket with a 50 ms timeout) and pins both windows to the pointer's output; elsewhere it shows at `lower`.

## Formatting

- `dialpad.py` uses CRLF line endings (DOS format). Adding code with LF endings triggers `git diff --check` whitespace warnings. Use `unix2dos dialpad.py` after editing if needed.
- Other files use standard LF.
